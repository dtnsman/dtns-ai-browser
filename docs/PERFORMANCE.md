## 0. 报告性质与诚实性声明

**本报告不含任何实测数字。**

所有性能判断来自两类可复核的推导：

1. **代码事实**：逐行阅读两版源码得出（§2、§3），给出了文件与行号，读者可自行核对。
2. **算术推导**：按各自的线格式（wire format）计算单条消息的字节数，以及「字节数 ÷ 带宽 = 传输时间」的换算（§4）。这是**算术，不是测量**。

因此：

- 文中「N 字节」是**按格式算出来的**，可复算；「M 毫秒」是**「字节 × 8 ÷ 带宽」的算术结果**，不含任何运行时因素（拥塞、慢启动、TLS 开销、代理设备处理）。
- 文中**没有**任何「实测 p50 = X ms」「吞吐 = Y req/s」这类数据，因为本报告按要求不做实测。
- §8 列出了必须实测才能定论的项目。

## 1. 一句话结论

> **v1 → v2 在网络层没有改变「一次请求 = 一个 WebSocket 往返」这个结构，因此延迟下限不变；改变的是「每个字节怎么装箱」——v2 用 13 字节固定头替代 JSON 的字段名开销，用原生字节替代 base64。结果是小响应省约 19%、二进制载荷省约 33% 的线字节。这部分收益只在「慢链路 + 大载荷」下可感知，在宽带下被 RTT 完全淹没。**

## 2. 事实基线：v1 线上跑的是 JSON，不是二进制

这一节是全部结论的前提，必须先纠正一个容易搞错的认知。

### 2.1 v1 的二进制协议文件是死代码

v1 插件目录里有 `protocol-bridge.js`（18 KB，完整二进制协议实现），但核查结果：

| 文件 | 对 `protocol-bridge` / `BinaryProtocol` 的引用次数 |
|------|--------------------------------------------------|
| `background.js` | **0** |
| `content-script.js` | **0** |
| `popup.js` | **0** |

且 `background.js` 内无任何 `encodeMessage` / `decodeMessage` 内联实现。它的实际收发是：

```js
// background.js:845
ws.send(JSON.stringify(message));

// background.js:872
const message = JSON.parse(data);
```

**结论：v1.0 生产实现是 JSON-over-WebSocket，`protocol-bridge.js` 未被接线。** 因此 v1 → v2 的真实网络差异是「**JSON 文本帧 vs 二进制帧**」，而不是「两套二进制编解码谁快」。

### 2.2 两版线格式对照

| 维度 | v1.0（线上） | v2.0 |
|------|-------------|------|
| 帧类型 | WebSocket **文本帧** | WebSocket **二进制帧** |
| 消息结构 | JSON 对象（字段名重复出现在每条消息里） | 13 字节固定头 + 定长/变长字段 |
| 固定头 | 无（JSON 语法 `{}`、`""`、`,`、`:` ≈ 与字段数成正比） | **13 B**：magic 4 + version 1 + type 2 + flags 2 + len 4 |
| 字符串编码 | JSON 字符串（需转义 `"` `\` 控制字符） | u16 长度 + 原始 UTF-8 |
| 二进制体 | **base64 后作为 JSON 字符串**（`background.js:972`） | 原生 `Uint8Array`（`http-proxy.js:517,541`） |
| 状态码 | JSON 数字（2–3 字符） | u16（v2 协议）／u8（v1 协议），2 B |
| 心跳间隔 | 30 000 ms（`background.js:692`） | 25 000 ms + 60 000 ms 看门狗（`transport.js:33,36`） |
| 单帧消息边界 | 由 WS 帧边界 + JSON 完整性确定 | 由 `len` 字段精确确定 |

> 注：v2 的帧头与 v1 的（未启用的）二进制设计一致，均为 13 B；差别在 status 字段宽度，v2 协议版本 2 用 u16 以支持非 100–599 的自定义状态。

## 3. 网络层专项对比（核心章节）

### 3.1 往返次数：完全相同

这是最容易被忽略、却最重要的一点。

| 项 | v1.0 | v2.0 |
|----|------|------|
| 一次 API 调用的往返次数 | **1** | **1** |
| 连接复用 | 单条长连 WebSocket | 单条长连 WebSocket |
| 请求流水线 | **无** | **无** |
| 多路复用（同连接并发请求） | **无** | **无** |
| 队头阻塞 | **有**（大响应阻塞后续小请求） | **有**（同左） |

**两版都把「一条消息 = 一个 WS 帧」作为原子单位**，没有把多个请求打包、也没有在一条连接上做多路复用。

这意味着：

```
端到端延迟 ≈ RTT × 1  +  传输时间(size / 带宽)  +  服务端处理  +  扩展处理
             ↑ 两版相同      ↑ 两版不同（v2 更小）      ↑ 两版相近
```

**RTT 项是延迟的主导项且两版相同**，所以「网络延迟」不会因为换协议而变好或变坏。差异全部落在**传输时间**项上，而这一项与载荷大小、链路带宽强相关（见 §3.4）。

### 3.2 单条消息的线字节：按格式推导

#### v2.0 的精确字节数（可逐项相加）

v2 的 HTTP 响应帧大小是确定的：

```
S_v2 = 13                                   // 帧头
     + (2 + |requestId|) + (2 + |domain|)   // 字符串：u16 长度 + UTF-8
     + 2                                    // u16 status
     + 2                                    // 头部字段个数（u16）
     + Σ_k (2 + |k| + 2 + |v|)              // 每个头部：两个字符串
     + 4 + |body|                           // 缓冲：u32 长度 + 原始字节
     + 1                                    // payload flags
     + (2 + |sseRequestId|) + (2 + |wsRequestId|) + (2 + |error|)   // 尾部字符串
```

#### v1.0 的字节数（估算，取决于字段名与转义）

```
S_v1 ≈ 固定开销(≈90–120 B：字段名 + JSON 语法)
     + |requestId| + |domain|               // 值的 UTF-8 字节
     + 3                                    // status 数字
     + Σ_k (|k| + |v| + 6)                  // 引号、冒号、逗号、引号
     + escaped(|body|)                      // 引号与反斜杠会被转义，+2 B/个
     + base64_inflation（若 body 是二进制：4/3 × N）
```

#### 算例（按上述公式代入）

设定：`requestId` 18 B、`domain` 43 B、2 个头部约 60 B、body 大小按下表。

| 场景 | body | v1.0 线字节 | v2.0 线字节 | v2 节省 |
|------|------|------------|------------|---------|
| `/api/info` 小响应 | 250 B JSON | ≈ 497 B | ≈ 401 B | **−19%** |
| 中等文本响应 | 1 024 B | ≈ 1 326 B | ≈ 1 179 B | **−11%** |
| 截图（v2 JPEG） | 49 152 B 二进制 | ≈ 65 656 B（base64） | ≈ 49 252 B | **−25%** |
| 截图（v1 PNG 典型） | 300 KB 二进制 | ≈ 400 120 B（base64） | ≈ 300 100 B | **−25%** |

> **关键观察**：文本 body 越大，v2 的相对优势反而**缩小**（19% → 11%），因为 v1 的固定开销（约 100 B）被大 body 摊薄了，而 v2 的优势主要来自「省掉固定 JSON 开销」而不是「省掉 body 本身」。
>
> 但**二进制 body 是另一回事**：v2 优势稳定在 **25%–33%**，且**不随 body 增大而衰减**，因为那是 base64 的固有膨胀（4/3），不是固定开销。

### 3.3 二进制载荷：结构性差距（唯一量级级差异）

base64 把 N 字节编成 `4 × ceil(N/3)` 字节，**恒定膨胀约 33%**；而且它多两趟整块处理（编码、嵌入 JSON 后的转义扫描）。

| 项 | v1.0 | v2.0 |
|----|------|------|
| 线字节（N=48 KB） | ≈ 65.7 KB | ≈ 49.3 KB |
| 线字节（N=300 KB） | ≈ 400 KB | ≈ 300 KB |
| 完全未压缩的全量遍历次数 | 3 遍（base64 / stringify / UTF-8 编码） | 0 遍（仅字节拷贝） |
| 线字节膨胀系数 | **×1.33** | **×1.00** |

**这是 v1 → v2 在网络层唯一可称为「结构性改进」的地方**：它不是实现细节的常数优化，而是**协议设计上少了一层编码**。

### 3.4 传输时间：把字节换算成时间（纯算术）

传输时间 = 字节 × 8 ÷ 带宽。下表完全是算术结果，**不含**拥塞、慢启动、TLS、重传等运行时因素。

**截图（48 KB → v1 65.7 KB / v2 49.3 KB，差 131 232 bit）**

| 下行带宽 | v1.0 传输 | v2.0 传输 | v2 节省 |
|---------|----------|----------|---------|
| 1 Mbps | 525 ms | 394 ms | **131 ms** |
| 5 Mbps | 105 ms | 79 ms | 26 ms |
| 20 Mbps | 26 ms | 20 ms | 6.6 ms |
| 100 Mbps | 5.3 ms | 3.9 ms | 1.3 ms |

**小响应（250 B → v1 497 B / v2 401 B，差 768 bit）**

| 下行带宽 | v1.0 传输 | v2.0 传输 | v2 节省 |
|---------|----------|----------|---------|
| 1 Mbps | 4.0 ms | 3.2 ms | **0.8 ms** |
| 5 Mbps | 0.8 ms | 0.6 ms | 0.15 ms |
| 20 Mbps | 0.2 ms | 0.16 ms | 0.04 ms |
| 100 Mbps | 0.04 ms | 0.03 ms | 0.008 ms |

**结论**：

- 小响应在任何带宽下，节省都在 **1 ms 以内**，相对 RTT（通常 20–100 ms）**不可感知**。
- 大截图在**慢链路**下节省可达 **百毫秒级**（1 Mbps 时 131 ms），这是真实可感知的改善。
- 在 20 Mbps 以上的链路，**两者差异进入噪声区**。

### 3.5 心跳与保活流量：v2 字节更少，但唤醒更频繁

| 项 | v1.0 | v2.0 |
|----|------|------|
| 心跳间隔 | 30 000 ms | 25 000 ms |
| 单帧字节 | ≈ 93 B JSON + 2–6 B WS 头 ≈ **95–99 B** | 13 + (2+20) + (2+24) = **61 B** + WS 头 ≈ 63–67 B |
| 每秒字节 | ≈ 3.2 B/s | ≈ 2.6 B/s |
| 每分钟唤醒 | 2 次 | 2.4 次 + 看门狗检查（本地，无流量） |

**结论**：

- **带宽上 v2 更省**（约 −19%），因为 13 字节头远小于 JSON 字段名。
- **唤醒次数上 v2 更多**（+20%），这是 CPU/电池维度的代价，与网络无关。
- 两者心跳流量都在**几字节每秒**量级，对任何链路都可忽略（折算约 0.02 kbps）。

### 3.6 丢包与重传暴露面

在丢包环境下，**消息越大 = TCP 段越多 = 暴露面越大**。

- v1 的 65.7 KB 截图约 `65.7 / MSS(≈1.4 KB) ≈ 47` 个段；v2 的 49.3 KB 约 `35` 个段。
- 段数减少约 **25%**，在相同丢包率下，**期望重传次数与恢复时间同比减少**。

这一项在**移动网络、弱 Wi-Fi** 下有实际意义：不仅传输更快，而且**更容易在丢包中「冲过去」**。

### 3.7 压缩：两版都没有实现，只能靠传输层协商

**先说结论：v1 和 v2 都没有实现任何应用层压缩。**

| 项 | v1.0 | v2.0 |
|----|------|------|
| 应用层压缩实现 | **无** | **无** |
| `FLAGS.GZIPPED (0x0010)` 常量 | 有定义（`protocol-bridge.js:51`，但该文件是死代码） | 有定义（`dtns-protocol.js:83`），**全项目零处使用** |
| `content-encoding` 处理 | 无 | 无 |
| WS 构造方式 | `new WebSocket(wsUrl)`（`background.js:768`） | `new WS(url)`（`transport.js:143`） |
| 压缩依赖 | 浏览器默认 offer `permessage-deflate` | 同左 |

v2 的 `FLAGS.GZIPPED` 是一个**预留但未接线的标志位**：协议里给它分配了位，但没有任何编码路径会设置它，也没有任何解码路径会读它。换言之——**能力位留了，功能没做**。

#### 传输层压缩对两版是「同等机会」

`permessage-deflate`（RFC 7692）是 WebSocket 层的扩展，**对文本帧和二进制帧同样生效**——它不是「只有 JSON 才能压」。两版都用默认构造函数建连接，Chrome 会自动 offer 该扩展。

所以真正的差异不是「谁被压缩」，而是**«内容有多可压缩»**：

| 内容类型 | 压缩率 | 说明 |
|---------|--------|------|
| v1 的 JSON 文本（小响应） | **高**（约 40%–60% 可省） | 重复字段名、结构可预测 |
| v2 的二进制帧头 + 字符串字段 | 中（约 20%–40%） | 同样有重复字符串，但基数本就更小 |
| v2 的 JPEG/PNG body | **≈0** | 已压缩数据，deflate 无效 |
| v1 的 base64(JPEG/PNG) body | **≈25%–33% 可省** | deflate 能把 base64 的膨胀基本还原 |

**关键推论（修正一个容易搞错的直觉）**：对大截图，**deflate 会把两版的差距抹平**——

- v1：300 KB PNG → base64 400 KB → deflate 后约 **300 KB**
- v2：300 KB 原始 → deflate 后约 **300 KB**

也就是说，**base64 的 33% 膨胀在启用 deflate 后基本被回收**，v2 在二进制载荷上的结构性优势会从 33% 缩到接近 0。而对小文本响应，v1 的 JSON 因为冗余度高，压缩后可能比 v2 更小。

#### 注意 deflate 的两个副作用

1. **每条消息独立压缩、上下文重置**：小帧压缩率差；极小的帧（如心跳，60–100 B）加上 deflate 的块头开销（约 5 B）甚至可能**净增大**。
2. **CPU 成本**：压缩/解压要消耗 CPU，虽远小于传输节省，但在「带宽充裕、CPU 紧张」的场景（如低端机）可能得不偿失。

#### 是否启用：无法从本仓库确认

隧道服务端是 `res2.dtns.top`（独立服务），其源码不在本工作区（`(内部站点)\site\server.js` 是官网 HTTP 服务，不是隧道服务端）。因此**是否协商成功 deflate 属于运行时行为**，已列入 §7/§8。

**验证方法**（一次握手即可确定）：看 WS 握手响应头是否含

```
Sec-WebSocket-Extensions: permessage-deflate
```

有则该扩展生效，§3.3、§3.4 的二进制优势需按上文折算；无则原结论成立。

#### 若要给 v2 补压缩，值得做吗？

| 场景 | 建议 |
|------|------|
| 大文本响应（HTML、JSON 列表） | **值得**：`FLAGS.GZIPPED` 已经预留，接上 `CompressionStream('gzip')` 即可，收益 50%+ |
| 截图/二进制 | **不值得**：JPEG/PNG 已压缩，纯 CPU 浪费 |
| 小响应（< 1 KB） | **不值得**：压缩开销与收益相抵，还可能增大 |

也就是说，**压缩的正确做法是按内容类型选择性启用**，而不是全量开启——这也解释了为什么 v2 预留了标志位却没有实现：它是一个需要服务端配合协商的能力，单方面实现无效。

#### 那么 nginx 层会不会做 gzip？

这是一个必须分清的边界问题，因为**整条链路有两个不同的网络段**，压缩规则完全不同。

```
                    段 A（公网 HTTP）              段 B（WebSocket 隧道）
API 客户端 ──────────────▶ nginx ────▶ 隧道服务端 ═══════════▶ 扩展 SW
        gzip 可作用于这段的响应体           nginx 无法 gzip WS 帧
```

| 层 | 能否压缩 | 作用于 |
|----|---------|--------|
| **nginx `gzip`** | 能，但**仅限 HTTP 响应体** | 段 A（客户端 ↔ nginx） |
| **nginx 对 WebSocket** | **不能** | 升级为 `101 Switching Protocols` 后，nginx 只做 TCP 转发，`gzip` 模块不参与 |
| **`permessage-deflate`** | 能，但需**上游 WS 服务端**实现 | 段 B（隧道帧，文本帧与二进制帧都适用） |
| **应用层 gzip** | 两版**都未实现** | — |

**关键点：nginx 的 gzip 永远压不到隧道帧。** 因为隧道帧（13 字节头 + 长度前缀 + 字段）只存在于「隧道服务端 ↔ 扩展」这段，到达 nginx 时已经被还原成普通 HTTP 响应体。所以 nginx gzip **不会缩小 §3.2 计算的任何隧道字节**，也**不会降低扩展侧的 CPU/内存开销**。

#### 实测核对（配置探测，非性能实测）

对 `browser2.wwz5g7mv8e1p183xt15g.html.dtns.top` 发送 `Accept-Encoding: gzip, deflate, br` 后读取响应头：

| 端点 | 响应体大小 | `content-encoding` | 是否被压缩 |
|------|-----------|-------------------|-----------|
| `/health` | 195 B | 无 | 否 |
| `/api/info` | 301 B | 无 | 否 |
| `/api/config` | 281 B | 无 | 否 |
| `/api/page/elements/simple` | **5 425 B** | 无 | 否 |
| `/api/page/visible-text` | 2 493 B | 无 | 否 |
| `/api/page/clickable-elements` | 2 176 B | 无 | 否 |

响应头 `server: nginx/1.14.1` 确认边缘是 nginx。用 5.4 KB 的响应体已可排除「低于 `gzip_min_length` 所以没压」的可能（nginx 默认 `gzip_min_length` 为 20 B）。

**结论：当前 nginx 对这些 API 响应没有做 gzip。** 即 `gzip` 未开启，或 `gzip_types` 未包含 `application/json`（nginx 默认 `gzip_types` 只有 `text/html`，且默认 `gzip off`）。

#### 隧道段（段 B）能否压缩：未验证，且不建议此时验证

隧道 WebSocket 走的是 `res2.dtns.top/tunnel`，**不经过 `browser2.*` 这个 vhost**（实测对该 vhost 发 `/tunnel` 升级请求返回的是 nginx 的 `404 text/plain`，说明该路径不由它提供）。

要确认段 B 是否协商 `permessage-deflate`，必须对 `res2.dtns.top` 发起真实握手。**但这会用同一个 `clientId` 注册第二个客户端，可能把正在运行的扩展挤下线**——本项目的隧道此前已因误操作中断过两次。因此**本报告不做此验证**，列为待确认项。

#### 三层压缩的净影响汇总

| 场景 | 段 A（nginx gzip） | 段 B（隧道） | 净效果 |
|------|-------------------|-------------|--------|
| 当前状态（已探测） | **关闭** | 未知 | **§3.2 的字节结论成立** |
| 若仅开启 nginx gzip | JSON 响应变小（估 50%+） | 不变 | **扩展侧毫无变化**；仅改善「调用 API 的客户端」的下载量 |
| 若仅开启 permessage-deflate | 不变 | 隧道字节下降 | 大截图优势被抹平（见上）；小文本 v1 可能反超 |
| 若两者都开启 | 双重收益叠加 | 隧道字节下降 | 客户端下载量最优，但压缩 CPU 成本翻倍 |


### 3.8 连接建立与故障恢复

| 项 | v1.0 | v2.0 |
|----|------|------|
| 握手消息 | JSON `register`，≈ 200 B | 二进制 `register_tunnel`，≈ 100 B |
| 握手次数 | 每次连接 1 次 | 每次连接 1 次 |
| 半开连接检测 | 依赖 `onclose`（TCP 半开时可能长时间不触发） | **60 s 看门狗**：心跳无 ack 即判定僵尸并重建 |
| 断线恢复 | 有重连（`maxAttempts` + `retryInterval`） | 有重连（退避 + 看门狗） |

**这是网络层里对「可用性」而非「吞吐」的改进**：v2 能识别「socket 还开着但对端已死」的僵尸连接，v1 在这种情况下会一直挂着直到用户手动重载。握手字节差异（100 B）仅在每次建连时发生一次，可忽略。

### 3.9 网络层小结

| 维度 | 谁更优 | 幅度 | 强度 |
|------|--------|------|------|
| 往返次数 | **平** | 0 | 强（结构相同） |
| 小文本响应字节 | **v2** | −11% ~ −19% | 强（可算） |
| 二进制载荷字节 | **v2** | **−25% ~ −33%** | 强（base64 固有膨胀） |
| 心跳带宽 | **v2** | −19% | 强（可算） |
| 心跳唤醒次数 | **v1** | v2 多 20% | 强 |
| 慢链路大载荷传输时间 | **v2** | 最多数百 ms | 中（算术，未含拥塞） |
| 宽带小载荷传输时间 | **平** | < 1 ms | 强 |
| 丢包暴露面 | **v2** | 段数 −25% | 中 |
| 队头阻塞 | **平**（都有） | — | 强 |
| 应用层压缩 | **都没有实现** | `GZIPPED` 标志位闲置 | 强（可查） |
| 启用 deflate 后的二进制载荷 | **趋于平** | base64 膨胀被回收 | 中（取决于协商） |
| 启用 deflate 后的小文本 | **可能 v1** | JSON 冗余度高 | **弱（未确认）** |
| 故障恢复 | **v2** | 由「不可知」变「60 s 内」 | 强 |

## 4. 非网络维度（简版）

### 4.1 每请求 CPU

| 环节 | 量级估计（推算，非实测） |
|------|------------------------|
| v2 代理层单请求（解码 + 路由 + 编码，小载荷） | 约 5–20 微秒 |
| 一次真实 `chrome.*` API 调用 | 1–20 毫秒 |

代理层比 Chrome API 低 2–3 个数量级。即使每秒 50 请求，代理层 CPU 也在个位数毫秒/秒，**< 1% 单核**。

### 4.2 编码侧分配与拷贝

按代码数出来的事实：

- v2 编码一个带 body 的响应，**body 被拷贝 3 次**（`encodeBuffer` → payload `concat` → `encodeFrame`），峰值内存 ≈ 3B。
- v1 编码文本 body，`JSON.stringify` + WS 层 UTF-8 编码，约 1 次字节拷贝 + 1 份字符串。
- v2 编码一次的临时小对象约 **33 + 8H** 个（H = 头部数）；若按 `protocol-bridge.js` 的写法约 27 + 6H——**v2 分配更多**，但它复用模块级 `TextEncoder`，而 `protocol-bridge.js` 每次调用都 `new TextEncoder()`。

**净效果方向相反、量级相近，无法静态断定谁总成本更低。**

### 4.3 常驻体积

| 项 | v1.0 | v2.0 |
|----|------|------|
| SW 代码 | 127 945 B（单文件） | 175 470 B（17 模块合并） |
| 差异 | — | **+37%**（但 v2 多 69 个端点） |

### 4.4 Service Worker 生命周期

两者都靠心跳维持存活（MV3 空闲约 30 s 回收）。v2 心跳更密（25 s vs 30 s）且多一个看门狗：

- **代价**：SW 更难深度休眠，电池场景后台唤醒略多。
- **收益**：僵尸连接可检测，断线可自动恢复。

这是 v1 → v2 唯一**用户可能间接感知**的常驻成本，量级在「每分钟个位数毫秒 CPU」。

## 5. 对扩展性能的影响（回答核心问题）

| 层面 | 影响 | 说明 |
|------|------|------|
| **CPU** | 可忽略 | 代理层每请求 5–20 μs，占单请求总耗时 < 1%；瓶颈始终是 Chrome API（ms 级） |
| **网络延迟** | 无变化 | 往返次数相同，RTT 主导且相同 |
| **带宽** | 下降 19%–33% | 慢链路 + 大载荷时可感知（1 Mbps 抓图省约 131 ms） |
| **内存峰值** | 略升 | v2 编码大 body 峰值约 3B；v1 处理大二进制约 1.33B 字节 + 2 份字符串 |
| **常驻唤醒** | 略升 | 心跳 25 s vs 30 s + 看门狗 |
| **可靠性** | 提升 | 僵尸连接 60 s 内可检测（v1 可能永久挂起） |
| **代码体积** | +37% | 一次性解析成本，毫秒级，不影响稳态 |

**一句话**：性能上不是「变快」或「变慢」，而是**把成本从「每次多发 33% 的字节」换成了「编码时多拷两次内存」**，并从「不知道连接死没死」换成了「60 秒内知道」。

## 6. 为什么「网络层」的收益在多数场景看不出来

这是本报告最需要说清的一点，否则容易得出错误结论。

一次真实调用的时间构成（示意，非实测）：

```
客户端 ──公网 RTT──▶ 隧道服务端 ──▶ 扩展 SW ──▶ chrome.* API
        20–50 ms              1–3 ms        1–20 ms
   ◀──── 返回路径 20–50 ms ────────────────┘
```

- v2 节省的**传输时间**在宽带下是**亚毫秒**；
- 而这条链路上**固定存在的 RTT 是几十毫秒**、**Chrome API 是几到几十毫秒**。

**所以：把线字节减半，端到端延迟也几乎不动。** 想真正改善延迟，唯一有效的手段是**减少公网往返**（就近部署隧道节点、复用连接、批量合并请求），而不是改序列化格式。

网络层的字节节省真正有价值的场景是：

1. **慢链路**（移动网络、弱 Wi-Fi）：抓图省百毫秒级；
2. **高频率抓图/大文件传输**：带宽与流量账单；
3. **丢包环境**：段数少 25%，恢复更快。

## 8. 结论

### 直接回答「单纯网络性能比较」

> **1. 延迟：完全相同。** 两版都是「一次请求 = 一个 WebSocket 往返」，RTT 主导且相同，不存在 v2 更快或更慢。
>
> **2. 字节：v2 更省。** 小文本响应省 **11%–19%**；二进制载荷（截图）省 **25%–33%**，后者来自 base64 的固有膨胀，是结构性改进。
>
> **3. 传输时间：只在「慢链路 + 大载荷」下可感知。** 1 Mbps 抓一张 48 KB 图，v1 需 ≈525 ms、v2 需 ≈394 ms，差 **131 ms**；20 Mbps 以上差异进入噪声（< 7 ms）；小响应在任何带宽下差异 **< 1 ms**。
>
> **4. 心跳：v2 字节更少（−19%）但唤醒更频繁（+20%）。** 带宽可忽略，电池维度略差。
>
> **5. 丢包：v2 段数少约 25%，弱网下更稳。**
>
> **6. 压缩：两版都没做。** v2 的 `FLAGS.GZIPPED`（`dtns-protocol.js:83`）是预留但未接线的标志位，全项目零使用；v1 同样没有实现。两版都只依赖浏览器默认 offer 的 `permessage-deflate`。
>
> **7. 若服务端启用了 deflate，结论会变：** 大截图的差距被抹平（deflate 能回收 base64 的 33% 膨胀，双方都趋近原始大小），小文本响应上 v1 的 JSON 因冗余度高可能反超 v2。**这一点未确认，是本报告最大的不确定性。**

### 建议

1. **不要为网络性能做架构改动**。延迟瓶颈是 RTT，不是序列化。
2. **若目标是省流量/弱网体验**，v2 的方向是对的，收益在大载荷上已经拿到。
3. **若目标是降延迟**，唯一有效方向是减少往返：就近节点、请求合并、连接复用——**与协议格式无关**。
4. **建议优先确认**：服务端是否启用 `permessage-deflate`。这一条会决定「小文本消息上 v2 到底省不省」，也决定是否需要为小响应单独做压缩策略。
