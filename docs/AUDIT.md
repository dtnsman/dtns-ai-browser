## 3. 架构与实现审计

### 3.1 分层结构

```
protocol (dtns-protocol)  纯字节编解码，37 种帧类型，无 I/O
   ↓
transport (transport/websocket)  WS 生命周期、注册、心跳、重连退避
   ↓
proxy (http-proxy/router)  HTTP 语义、CORS、鉴权、请求→帧→响应
   ↓
agent (browser-agent/routes)  69 条端点，Express 风格路由表
   ↓
adapter (chrome-adapter)  chrome.* 的 Promise/回调统一封装
```

**评价**：分层边界清晰，每层可独立测试（协议纯函数、路由无 socket、传输真实 TCP、端到端真实 socket）。这是本次测试能达到 94% 行覆盖率的**结构性原因**，而非靠堆用例。

### 3.2 与 sdk.js 的一致性

| 维度 | 审计结果 |
|------|---------|
| 帧头布局（MAGIC/version/type/flags/length） | 与 sdk.js 逐字段一致，由 `protocol.test.js` 字节级固化 |
| 状态码宽度 | v2 用 u16、v1 用 u8 —— 与线上服务端协商结果一致（真机 `protocolVersion: 2`） |
| 能力帧先于注册帧 | 顺序被 `transport.test.js` 断言 |
| 域名协商 | `browser2.*` 前缀经真机验证为 v2 通道；`browser.*` 保持指向 v1.0 服务 |

**关键决策复核**：将默认前缀从 `browser` 改为 `browser2` 是**必要且正确**的。`browser.*` 在服务端被硬编码路由到 v1.0 JSON 代理，二进制帧会被误解析。该决策有真机证据（`/api/config` 返回 `browserDomain=http://browser2.…` 且 `/health` 报 `protocolVersion: 2`）。

### 3.3 代码质量观察

| 项 | 评价 |
|----|------|
| 模块职责 | 单文件最大 903 行（`routes.js`），属端点表驱动，可接受；其余均 < 600 行 |
| 错误处理 | 统一 `ProxyError` + `status` 映射，路由层有 `exposeErrors` 开关控制信息泄露 |
| 异步正确性 | 本次审计修复了 `invoke()` 的同步/回调判定缺陷（见 §4.1），其余无发现 |
| 资源释放 | debugger 引用计数、截图缓存 LRU、WS close 幂等均有实现与用例 |
| 注释 | 关键决策（如 `localPort` u8 约束、响应先于重绑）均有就地说明 |

## 4. 缺陷审计

### 4.1 已修复缺陷（9 项，均有回归用例固化）

| # | 严重度 | 现象 | 发现途径 |
|---|--------|------|---------|
| 1 | 高 | `decodeMessage` 不解码 `register_tunnel`/`heartbeat`/`capabilities`，传输层拿不到 clientId | 单测 |
| 2 | 中 | `NetworkMonitor` 提前 return，DevTools 关闭后状态不复位 | 单测 |
| 3 | 中 | `sniffImage` 对 `Uint8Array` 重复按 base64 解码，宽高返回 null | 单测 |
| 4 | 低 | HEAD 响应 `Content-Length` 为 0 | 单测 |
| 5 | 高 | 改 clientId 时先重绑后响应，响应帧落在已关闭 socket | 单测 |
| 6 | 中 | 注册被拒时重试计数在 `onopen` 归零，退避失效 | 单测 |
| 7 | 高 | `localPort: 10999` 被 u8 静默截断为 247 | 协议审阅 |
| 8 | 低 | 并发测试触发 `MaxListenersExceededWarning` | 单测（测试基建） |
| 9 | **高** | `ChromeAdapter.invoke()` 用 `fn.length <= args.length` 判定同步 API，真实 Chrome 下回调前就 `resolve(undefined)`，导致 `/api/tabs/list` 500、全部标签页接口失效 | **真机联调** |

**第 9 项是本项目最有价值的发现**：185 个本地用例（含 mock chrome）全部通过，因为 mock 一律返回 Promise，走不到该分支。这直接证明「真机联调」不是形式主义，而是不可替代的一层。修复后补了 3 个「返回 undefined + 异步回调」的回归用例，旧代码在用例下必失败。

联调后续又暴露了 4 个同类缺陷（`ConfigStore` 默认值被 undefined 覆盖、`wsServerUrl` 缺 `/tunnel` 路径、
`navigator.clipboard` 同步抛错、`/api/click/at` 一次点击触发两次），均已修复并补用例，
详见 [LIVE-TEST.md](LIVE-TEST.md) §4。

### 4.2 未修复 / 接受的风险

| # | 风险 | 影响 | 处置建议 |
|---|------|------|---------|
| R1 | SSE / 流式响应返回 501 | 无法代理 EventSource 类接口 | 协议帧是「一问一答」模型，需扩展帧类型；当前明确不支持并已文档化，可接受 |
| R2 | v1 协议状态码截断（404→148） | 仅影响 `browser.*` v1 通道 | 本版不走 v1；若未来回退需注意 |
| R3 | `token: ''` 默认无鉴权 | 任何知道域名者可控制浏览器 | **生产部署必须设置 token**，已在 `background.js` 注释与 API 文档标注 |
| R4 | MV3 Service Worker 可能被回收 | 隧道中断，需事件唤醒 | 心跳 + WebSocket 活动在 Chrome 116+ 通常可保活；未做数小时观察（见 §6） |
| R5 | debugger 类端点与用户 DevTools 互斥 | 网络/控制台采集失败 | 已有 `CHROME_API_ERROR` 映射与错误透出；使用方需知悉 |

## 5. 安全审计

| 检查项 | 结果 |
|--------|------|
| 硬编码密钥/口令扫描 | ✅ 未发现（`src/`、`background.js`、`popup.js`） |
| 外部网络外联 | 仅 `wss://res2.dtns.top`（隧道）与 Chrome 商店 URL（注入排除名单），无遥测/上报 |
| `eval` 使用 | 仅 `content-script.js:47`（`/api/script/evaluate` 的既有语义），与旧版一致，未新增攻击面 |
| 扩展权限 | `debugger`、`<all_urls>`、`webRequest` 均为功能必需；`scripting` 仅在注入回退时使用 |
| CSP | `script-src 'self'; object-src 'self'`，无 `unsafe-eval`（MV3 强制） |
| 错误信息泄露 | 默认 `exposeErrors: false`，内部错误统一为 `internal_error` |
| 鉴权实现 | Bearer + `?token=` 双通道；`www-authenticate` 正确返回 |

**审计意见**：无高危问题。R3（默认无鉴权）是**部署配置问题而非代码缺陷**，但必须在交付说明中显著提示——当前 `README` 与 `extension/README.md` 已有说明，建议在上线检查单中列为强制项。

## 6. 测试有效性审计

### 6.1 分层真实度评估

| 层 | 真实度 | 审计意见 |
|----|--------|---------|
| 协议 | 字节级 | 手工构造字节，可发现布局错误 |
| 路由 | 无 socket | 快，但不覆盖网络行为 |
| 传输 | 真实 TCP + 自建 RFC6455 服务端 | **高价值**：握手/掩码/分片均真实 |
| 端到端 | 真实 socket | 覆盖帧序与并发 |
| 浏览器能力 | mock chrome | **本次被证明有盲区**（见 §4.1 第 9 项） |
| 真机联调 | 真实 Chrome + 真实隧道 | **不可替代**，已覆盖 68/69 条路由（72 项检查） |

### 6.2 覆盖盲区

1. **`config/clientId/generate` 未在真机执行**：会更换域名并可能让 Service Worker 休眠，已确认
   与已验证的 `config/reset`、`config/clientId` 共享同一代码路径，本地用例覆盖。
2. **`smart_reply` 成功路径**：依赖外部服务，本机不可达，仅验证端点响应确定性。
3. **剪贴板在窗口聚焦下的稳定性**：受 Chrome 安全策略影响，窗口失焦时必然失败（聚焦时通过）。
4. **长时间稳定性**：真机 `uptimeMs` 峰值观测约 57 分钟连续在线，未做小时级观察。
5. **多浏览器**：仅 Chrome 系。

**审计意见**：测试体系设计优秀（真实 TCP、真实产物、真机联调三层递进）。真机覆盖率已从初期的
19/69 提升到 **68/69 ≈ 98.6%**，写操作全部在专属靶场页面 `test-fixture.html` 上完成并有副作用断言。

## 9. 结论与建议

### 9.1 总体结论

**可交付（附条件）**。

- 功能完整性：69 条端点全部实现，真机抽样 19 条验证通过；
- 测试充分性：185 用例 / 94.14% 行覆盖 / 72 项真机联调，证据链完整且可复跑；
- 与线上协议兼容性：帧格式、状态码、域名协商均已验证；
- 未发现高危安全缺陷。

**附条件**指 §4.2 的 R3 与 §8 的工程化缺口需在正式上线前落实。

### 9.2 优先级建议

| 优先级 | 事项 | 理由 |
|--------|------|------|
| P0 | 生产部署设置 `token` | 否则等于把浏览器控制权公开在公网域名上 |
| P0 | `git init` + 基线提交 | 当前无版本追溯能力，风险不可控 |
| P1 | 在空白靶场标签页补写操作联调（click/type/navigate） | 真机覆盖仅 28%，mock 与真机已证明存在差异 |

| P2 | 建立最小 CI（`node --test` + 覆盖率阈值） | 防止后续回归 |
